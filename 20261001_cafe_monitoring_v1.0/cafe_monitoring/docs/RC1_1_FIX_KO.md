# V10 10.0.0-rc1.1 설치 검사 수정

사용자가 제공한 2026-09-30 Windows / Python 3.14 로그에 대응한 수정입니다. 의존 패키지 설치는 성공했고, 설치 후 자동검사에서 실패했습니다.

| 관찰 | 확인된 원인과 수정 |
|---|---|
| 한글 JSON을 읽을 때 cp949 UnicodeDecodeError | 검사 코드 두 곳에 UTF-8 지정이 빠져 있었습니다. 두 곳과 DB 스키마 읽기에 UTF-8을 명시하고, 설치·시작·검사 BAT 모두 Python UTF-8 모드를 설정했습니다. |
| 이관·백업 검사 정리 중 백업 SQLite 파일 WinError 32 | SQLite 연결을 with 문으로 쓰기만 하면 연결이 닫히지 않습니다. 운영 백업 코드와 검사 코드에 명시적인 닫기를 추가했습니다. 백업 도중 예외가 발생해도 닫히게 했습니다. |
| 4624 != 3 | 시험에서 3바이트를 쓰도록 했지만 등록된 파일 크기는 4,624바이트였습니다. 해당 PC에서 크기가 달라진 원인은 미확정입니다. 파일 무결성 검사는 Office 파일이 아닌 일반 바이너리 시험 자료로 수행하고 실제 저장 크기를 대조합니다. 변경한 바이트의 해시가 달라지는지, 변경·삭제를 각각 FILE_CHANGED·FILE_MISSING으로 거부하는지 확인합니다. 실제 운영 PPT의 SHA-256 검증은 변경하지 않았습니다. |
| HTTPError 관련 ResourceWarning | 검사에서 HTTP 응답과 예외 응답을 명시적으로 닫았습니다. |

## 수정 전후 직접 실행 증거

- 수정 전: 한글 기본 인코딩을 CP949로 지정하여 동일한 UnicodeDecodeError를 재현했습니다.
- 수정 전: 백업 직후 연결 추적 결과 원본은 닫혔지만 대상 백업 연결은 열려 있었습니다: `[True, False]`.
- 수정 후: V10 검사 33개 통과. 기존 31개에 백업 성공·실패 양쪽의 연결 해제 검사 2개를 추가했습니다.
- 수정 후: Linux에서 기본 파일 인코딩을 CP949로 모의한 V10 검사 33개 모두 통과했습니다. 기본 인코딩 지정이 없는 텍스트 열기만 CP949로 바꾸고 명시된 UTF-8 처리는 유지한 조건입니다.
- JavaScript 로직/API 계약 19개 통과. Python 컴파일과 JS 문법 검사 통과.
- 기존 엔진 검사 54개는 초기 RC1에서 수행한 결과입니다. 이번 수정에서 엔진 기능은 변경하지 않았고 다시 실행하지 않았습니다.

## 적용

V10 실행 콘솔을 종료한 뒤 ZIP의 `naver_cafe_v10` 폴더 내용을 기존 같은 폴더에 덮어씁니다. 기존 `.venv`와 `data_v10` 폴더를 삭제하지 마세요. 수정본은 이 두 폴더를 포함하지 않습니다. 이미 패키지 설치를 마쳤으므로 `03_verify_v10.bat`를 실행해 `Ran 33 tests`와 `OK`를 확인한 다음 `02_start_v10.bat`를 실행합니다. 새 설치는 `01_setup_v10.bat`부터 시작합니다.

## 아직 확인되지 않은 부분

Windows OS에서 수정 후 재실행, 실제 PowerPoint·네이버·AI·Outlook·브라우저 화면 동작은 이번 검사로 확인하지 않았습니다. 4,624바이트 현상을 특정 보안 프로그램이나 DRM 때문이라고 단정할 수 없습니다. 실제 PPT도 해시 오류가 난다면 그 실행 기록을 따로 확인해야 합니다.
