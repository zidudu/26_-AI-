# GitHub·Google Drive 공유 및 업데이트 확인

고정 기본 배포 경로는 **`https://github.com/zidudu/26_-AI-/tree/main`**입니다. 저장소는 `zidudu/26_-AI-`, 대상 브랜치는 `main`입니다. 별도 요청이 없으면 이 저장소 안에 프로젝트를 추가·갱신합니다. 다른 세션에서도 이 주소를 다시 요청하지 않습니다. 사용자가 명시적으로 다른 주소나 Drive 폴더를 지정하면 그 대상을 우선합니다. 프로젝트와 버전은 해당 요청과 실제 소스에서 확인하며 임의로 정하지 않습니다.

## 짧은 요청의 해석과 대상 선택

- `깃헙`·`깃허브`·`GitHub`는 같은 대상이며, `구드`·`구글드라이브`·`Google Drive`도 같은 대상입니다. "깃헙 구드 업로드 해"는 아래 공유용 배포 절차 전체를 수행하라는 요청입니다. ZIP, 구조도, 캡처를 사용자가 매번 다시 나열할 필요는 없습니다.
- 대상은 현재 세션에서 수정하거나 완성한 프로젝트입니다. 방금 만든 배포 ZIP, 소스 경로, 버전과 검증 결과를 대화에서 먼저 확인합니다. 문맥으로 특정할 수 있으면 프로젝트를 다시 묻지 않습니다.
- 로컬 프로젝트에 Git 원격이 없어도 기본 저장소를 사용합니다. 기본 저장소를 별도 작업 폴더에 받아 기존 구조에 맞는 프로젝트 하위 경로에 추가하거나 갱신합니다. 프로젝트 전용 저장소가 없다는 이유로 새 GitHub 저장소를 만들지 않습니다.
- Drive는 사용자 지정 또는 해당 세션에서 확인한 배포 폴더를 우선합니다. 지정이 없으면 대응 프로젝트 폴더를 검색하고, 대응 폴더가 없으면 내 드라이브에 프로젝트명으로 폴더를 만들어 배포합니다. 동명 후보가 여러 개라 대상을 특정할 수 없을 때만 위치를 확인합니다.

## 저장소 안의 배치

실행 시 `main`의 최신 트리를 먼저 읽고 기존 규칙을 따릅니다. 2026-10-02에 확인한 루트에는 `20261001_arca_archive_v2.2.1`, `20261001_cafe_monitoring_v1.0`, `20261001_local_ai_workbench_v0.1`, `20261001_youtube_media_library_v8_beta2`가 있었습니다. 이 목록은 배치 예시이며 현재 파일 목록은 다시 조회합니다.

같은 프로젝트·버전의 보완은 해당 폴더에 반영하고, 새 프로젝트나 새 배포 버전은 `YYYYMMDD_프로젝트식별자_v버전` 형태의 하위 폴더를 만듭니다. 그 안에 소스, 실행 안내와 Mermaid 구조도가 있는 `README.md`, 실제 캡처를 담는 `screenshots/`, 공유 ZIP을 배치합니다. 기존 ZIP 위치가 있으면 유지하고 새 폴더에서는 `releases/`를 사용합니다. 루트 `README.md`의 프로그램 목록에도 해당 프로젝트 링크와 버전을 반영합니다. 다른 프로젝트의 파일과 최근 변경을 보존합니다.

## 공유용 배포 요청을 받았을 때

1. 실제 소스와 실행 방법을 확인하고, 공유에 필요한 파일만 담은 ZIP 하나를 만듭니다. 비밀키, 개인 데이터, 캐시, 가상 환경, 불필요한 대용량 파일을 제외합니다. 원본 소스는 보존합니다.
2. GitHub의 해당 프로젝트 설명에 **실제 코드에 근거한 Mermaid 시스템 구조도**를 넣습니다. 실행한 제품의 **실제 화면 캡처 여러 장**을 GitHub에 올리고 문서에서 볼 수 있게 연결합니다. 다른 사람의 글이나 내용이 화면에 나오면 테스트 서버와 테스트 데이터로 화면을 다시 캡처합니다. 합성 화면을 실제 캡처라고 표기하지 않습니다.
3. 같은 공유용 ZIP을 로컬, 지정 GitHub 저장소, 연결된 Google Drive에 올립니다. GitHub 저장소 파일이나 Release 자산 중 적절한 위치를 선택하고, 각 위치의 링크와 버전을 기록합니다. GitHub에는 ZIP과 함께 프로젝트 소스, 실행 안내, Mermaid 구조도, 실제 캡처가 담긴 문서도 반영합니다.
4. ZIP을 열어 내용과 실행 안내를 검사하고 SHA-256을 기록합니다. 업로드 후 GitHub와 Drive의 파일을 다시 조회해 버전, 크기, 가능하면 해시 또는 다운로드한 내용까지 대조합니다. 완료 보고에는 세 위치, 커밋 또는 Release, ZIP 해시, 캡처 및 구조도 확인 결과를 넣습니다.

## 업데이트 여부만 물었을 때

GitHub 기본 브랜치의 최신 커밋과 해당 프로젝트 파일을 확인하고, Drive에서 프로젝트명·버전명으로 대응 자료를 찾습니다. 이름만 같다고 같은 배포본으로 단정하지 않습니다. 파일명, 버전, 수정 시각을 대조하고 필요한 경우 내용이나 해시를 비교합니다. 각 위치를 `확인됨`, `미반영`, `확인 불가`로 보고하며 근거 링크와 확인 시각을 붙입니다. 수정 시각만으로 ZIP 내용 일치를 판정하지 않습니다.

조회 요청만으로 업로드나 동기화를 시작하지 않습니다. 배포 요청이 있어도 대상 프로젝트가 특정되지 않으면 임의의 프로젝트를 배포하지 않습니다.
