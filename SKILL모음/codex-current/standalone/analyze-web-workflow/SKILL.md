# 웹 동작 분석·자동화

실제 사용자가 수행하는 동작을 관찰 가능한 근거와 연결하여 설명하고, 요청한 범위의 자동화를 구현하거나 수리하라. 사용자가 말하는 ‘복호화’는 문맥상 웹 동작 분석으로 이해하되, 이미 의미가 명확하면 용어 확인으로 작업을 지연하지 마라.

## 요청에 맞춰 시작하라

- **원리 설명:** 화면과 코드로 확인한 동작 및 아직 모르는 부분을 설명하라. 구현·설치·실제 저장까지 임의로 확장하지 마라.
- **새 자동화:** 대상 업무를 분석한 뒤 재사용 가능한 실행 흐름과 사이트별 설정을 분리하여 구현하라.
- **기존 오류 수정:** 가장 먼저 실패하는 단계의 실제 동작을 재현하고, 근거가 확인된 부분부터 좁게 수정하라. 정상 동작하는 흐름을 불필요하게 재작성하지 마라.

URL·대상 목록·작업 순서·완료 기준·기존 파일은 현재 요청과 대화에서 먼저 확인하라. 정보가 부족해도 제공된 파일·화면으로 가능한 분석은 진행하고, 다음 단계에 꼭 필요한 정보만 질문하라. 기존 업무의 권한·담당자·날짜 규칙을 다른 사이트의 새 작업으로 옮기지 마라.

## 접근 수단과 증거 범위를 확인하라

현재 환경에서 제공되는 앱·브라우저·파일 도구의 기능과 제약을 먼저 확인하라. 브라우저 작업에는 제공된 브라우저 스킬과 런타임 문서를 따르고, 로그인은 그 환경이 지정한 인증 절차로 처리하라. 이 스킬 자체가 사용자 PC의 탭이나 사내망에 대한 접근 권한을 제공하지는 않는다.

브라우저에서 DOM·스크립트·네트워크·이벤트를 어느 수준까지 볼 수 있는지 구분하라. 현재 도구가 제공하지 않거나 금지하는 검사를 외부 브라우저, 임의 코드 실행, 숨겨진 상태 탐색으로 우회하지 마라. 필요하면 사용자 제공 코드, 관련 HTML 조각, 민감정보를 제거한 요청 기록으로 분석을 이어가라. 스크린샷만으로 이벤트 종류나 API 필드를 확인했다고 표현하지 마라.

현재 작업에 필요한 범위만 수집하고, 비밀번호·쿠키·인증 헤더·토큰을 스킬, 결과물, 로그에 포함하지 마라. 로그인·권한 제한을 우회하지 마라. 분석 요청만으로 외부 기록을 변경하지 말고, 현재 작업에서 이미 승인된 변경은 중복 승인 없이 수행하라.

## 정상 동작을 작은 단위로 연결하라

실패하는 팝업·달력·행 편집기는 **실제로 열린 상태**에서 확인하라. 다음 관계를 필요한 단계만큼 기록하라.

`시작 상태 → 입력 대상과 동작 → 로딩 또는 요청 → 도착 상태와 검증 조건`

각 단계에서 다음을 구분하라.

- **대상:** 현재 탭·프레임·활성 팝업, 입력 요소의 식별자, 결과 행의 업무 키와 열.
- **동작:** 실제 사용자 입력으로 성공하는 클릭·더블클릭·키 입력·선택 순서.
- **준비 상태:** 요소가 보이는 것과 이벤트 처리·데이터 로딩 준비가 끝난 것의 차이.
- **결과:** 표시 문자열, 선택 값, 행 데이터 또는 허용된 응답에서 확인한 변화.

직접 관찰, 제공 파일에서 확인, 이전 대화의 보고, 추정을 구분하라. 이전 사이트의 선택자·라이브러리·이벤트를 새 사이트의 사실로 취급하지 마라. 공개 문서가 필요하면 관찰한 제품·버전에 맞는 공식 자료를 확인하라.

## 차이가 발생한 계층을 수정하라

클릭 대상을 좌표나 이름만으로 추정하지 말고 현재 화면 범위와 업무 키로 좁혀 유일성을 확인하라. 이름이 같은 후보가 여럿이면 첫 번째 요소를 임의로 선택하지 마라. 빈 결과 셀과 숨겨진 원본 요소도 구분하라.

사람의 정상 동작과 자동화 동작을 비교하여 **대상 지정 → 입력 이벤트 → 준비 상태 → 요청 식별 → 결과 판정** 중 어디서 처음 달라지는지 찾으라. 타임아웃을 늘리거나 이벤트를 전부 보내는 수정부터 시작하지 마라.

팝업, 달력, 프레임, 가상 표, 중복 요청 및 입력 이벤트 문제는 [interaction-diagnostics.md](references/interaction-diagnostics.md)의 해당 항목을 읽어라.

## 요청된 자동화를 완성하라

공통 실행기는 대기·중단·재개·로그·결과 확인을 담당하게 하고, 사이트별 부분에는 선택자·이벤트·요청 식별 조건·업무 규칙을 두라. 단순한 한 단계 작업을 위해 범용 엔진을 먼저 만들지는 마라.

날짜·담당자·검색값·처리 범위는 입력 또는 명시된 업무 규칙으로 제공하라. 실제 기록을 수정하는 값은 사용자 지시와 검증 가능한 데이터에 근거하라. 화면의 유효성 검사를 통과하려고 날짜나 상태를 임의로 만들어내지 마라.

반복 처리, 화면 전환, 저장과 재개가 있으면 [reliable-automation.md](references/reliable-automation.md)를 읽고 적용하라. 사용자가 분석만 요청했다면 필요한 설명까지 마치고 이 구현 단계는 생략하라.

## 검증 수준을 정확히 보고하라

가능한 범위에서 기존 오류를 재현하고 수정 후 관찰되는 결과를 비교하라. 실제 라이브러리나 화면을 쓸 수 있으면 활용하고, 모의 화면은 실사이트와 같은 것으로 간주하지 마라. 새로운 테스트는 해당 실패나 저장 중복 같은 구체적인 위험을 검증할 때 추가하라.

외부 기록 변경을 포함하는 검증은 현재 업무에서 허용된 범위 안에서 수행하라. 저장 이후 결과가 불명확하면 재조회로 확인하고, 중복 저장을 유발하는 재시도로 검증하지 마라.

결과를 한국어 존댓말로 설명하라. 원인, 변경 내용, 검증한 범위, 남은 불확실성, 필요한 사용 방법을 담되, 간단한 분석에는 불필요한 장문 보고서를 만들지 마라. 코드 검토·모의 실행·실사이트 일부 동작·전체 저장 검증을 명확하게 구분하라.
