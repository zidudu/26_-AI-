# 화면·이벤트·요청 진단

해당 오류와 관련된 항목만 사용하라. 아래 내용은 확인할 가설이며, 특정 라이브러리나 이벤트를 모든 사이트에 적용하라는 지시가 아니다. 도구가 허용하는 검사와 제공된 파일만 이용하라.

## 입력 대상을 식별하라

- 검색 영역, 결과 표, 숨겨진 템플릿에 같은 라벨이 있는지 구분하라. 활성 영역 안의 실제 입력 가능한 요소를 찾으라.
- 안정적인 ID·name·역할·라벨 연결·열 키를 실제 DOM에서 확인하여 사용하라. 동적으로 바뀌는 식별자나 행 순번에만 의존하지 마라.
- 가상 표에서는 보이는 행만 DOM에 있을 수 있다. 일반 `table`·`td` 구조를 전제하지 말고 표 컴포넌트의 실제 행·셀 구조와 스크롤 컨테이너를 확인하라. 렌더링된 행 수를 전체 결과 수로 간주하지 마라.
- 빈 셀은 텍스트 검색으로 찾지 못한다. 먼저 업무 키로 행을 식별한 후 열 키로 해당 셀을 찾으라.
- 프레임·새 탭·활성 팝업으로 전환된 뒤에는 그 문맥에서 요소를 다시 찾으라. 연결이 끊긴 이전 요소 핸들을 재사용하지 마라.

## 입력 이벤트와 준비 상태를 분리하라

1. 가능하면 지원되는 브라우저 입력 기능으로 수동 성공 동작을 한 번 수행하라.
2. 입력값 표시, 포커스, 요청 발생, 결과 표시 중 실제로 어디까지 성공했는지 기록하라.
3. 이벤트를 확인할 수 있는 소스 또는 허용된 관찰 기능이 있으면 성공 경로의 핸들러와 준비 조건을 비교하라.
4. 코드가 준비되었다는 근거가 된 상태를 기다린 후, 실제 성공 경로에 필요한 입력을 보내라.

값이 화면에 보이는 것만으로 앱의 내부 입력 상태가 갱신되었다고 판단하지 마라. 프레임워크 제어 입력은 사용자 입력과 단순 DOM 값 대입이 다른 결과를 만들 수 있다. DOM 값만 바꾸고 제출하는 방식이 문제라면 지원되는 입력 API부터 사용하라.

`keydown`, `keypress`, `keyup`, 폼 `submit` 중 어떤 경로가 검색을 실행하는지 증거로 구분하라. Enter가 실패한다고 이 이벤트들을 무조건 모두 보내면 중복 검색·제출이 발생할 수 있다. 과거의 레거시 코드가 숫자 키 코드 13을 확인했다는 사실은 새 사이트도 그렇다는 근거가 아니다.

팝업이 보이더라도 트리 데이터, 검색 인덱스, 이벤트 핸들러가 아직 준비되지 않았을 수 있다. 실제로 관찰된 준비 상태를 사용하고, 검색 후에는 결과 존재와 선택 완료를 별도로 확인하라. 동명이인은 부서나 다른 업무 식별 정보로 구분하라.

## 달력과 선택 위젯을 확인하라

열린 위젯의 현재 모드, 표시 연도·월, 선택 가능한 셀, 최종 입력값을 확인하라. 목표 날짜가 같아도 시작 모드와 연도가 다르면 필요한 조작은 달라진다.

일부 위젯은 `click` 외에 포인터·마우스 이벤트나 포커스 처리에 의존한다. `click()` 호출과 실제 브라우저 입력의 결과가 다르면 로드된 라이브러리 또는 정상 입력 기록에서 이유를 확인하라. 증거 없이 이벤트 순서를 고정하거나 입력창 표시값만 덮어쓰지 마라.

가능한 경우 키보드 입력이나 위젯의 지원 인터페이스도 검토하되, 현재 도구의 허용 범위 안에서 사용하라. 최종 저장에 사용되는 값이 목표 값과 일치하는지 확인하라. 날짜의 의미, 시간대, 말일 처리, 발생일과의 관계는 사이트 업무 규칙에서 정하라. ‘30일’과 ‘달의 마지막 날’을 혼동하지 마라.

## 요청을 업무 단위로 식별하라

관찰 가능한 경우 한 동작의 요청을 URL 경로, 메서드, 요청 필드, 응답 구조, 실행 시점으로 구분하라. 동일 검색 문자열이 들어 있다는 이유만으로 본문 조회와 보조 조회를 같은 요청으로 취급하지 마라.

이전 검색 응답이 늦게 도착하는 상황을 고려하라. 현재 입력·작업 키와 해당 실행의 결과가 연결되는지 확인하고, 구분할 근거가 없으면 자동 판정을 중단하라. ‘정상적으로 여러 요청 발생’과 ‘사용자 동작의 중복 실행’을 구분하라.

HTTP 성공만으로 업무 성공을 판단하지 마라. 응답이 로그인 페이지, 검증 실패, 빈 결과 또는 이전 조회 결과일 수 있다. 응답과 최종 화면의 업무 키·상태를 함께 확인하라.

내부 엔드포인트를 발견했다는 이유만으로 직접 요청 방식으로 바꾸지 마라. 지원 API가 있으면 검토하고, 직접 요청은 도구가 허용하며 요청 범위에 맞고 인증·업무 검증을 보존할 수 있을 때만 선택하라. 인증정보가 담긴 요청 전체를 결과물에 복사하지 마라.

## 타임아웃을 진단 가능한 오류로 바꾸라

`결과 대기 실패` 대신 실패 단계, 현재 URL 또는 화면명, 검색한 업무 키, 기대한 조건, 마지막 관찰 상태를 남기라. 관련 없는 개인정보나 전체 페이지 덤프는 포함하지 마라.

조건 자체가 잘못되었는지, 입력이 전달되지 않았는지, 로딩이 느린지, 응답이 실패했는지를 먼저 확인하라. 관찰된 정상 지연이 근거가 될 때 대기 시간을 조정하라. 재시도는 전체 업무가 아니라 결과가 없다고 확인된 안전한 단계에 한정하고 횟수를 제한하라.

## GQIS 사례에서 가져온 확인 질문

다음은 이전 대화에서 보고된 사례를 일반화한 참고다. 현재 사이트나 새 버전에서 직접 재확인한 결과로 표현하지 마라.

| 당시 보고된 현상 | 다른 업무에서 확인할 질문 |
|---|---|
| 일반 표 탐색으로 결과 셀을 못 찾음 | 실제 결과가 `div` 기반 가상 표인가? 행과 열의 키는 무엇인가? |
| 이름을 입력했지만 검색 결과가 없음 | 입력 이벤트가 검색을 실행했는가? 팝업 내부 데이터는 준비됐는가? |
| 달력 제목·월 선택이 진행되지 않음 | 정상 입력과 자동 입력의 이벤트 및 포커스 처리가 다른가? |
| 같은 번호를 포함한 요청이 여러 개임 | 본문·부품·보조 데이터 요청을 구분했는가? |
| 저장 확인 후 복귀 버튼을 못 찾음 | 스크롤 컨테이너나 화면 상태가 바뀌었는가? |

이 사례의 담당자, 날짜, 대상 목록, 저장 횟수 및 선택자를 새 업무의 기본값으로 사용하지 마라.
