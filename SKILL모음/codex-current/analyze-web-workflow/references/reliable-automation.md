# 반복 업무의 실행·저장·복구

## 사이트 규칙과 실행 흐름을 나누라

공통 부분에는 제한된 조건 대기, 취소, 단계 로그, 진행 위치, 확인 후 다음 건 이동을 두라. 사이트별 부분에는 다음처럼 실제 확인한 값만 두라.

| 설정 | 포함할 내용 |
|---|---|
| 입력·범위 | 원본 파일/행, 업무 키, 처리 대상과 제외 조건 |
| 화면 식별 | 목록·상세·팝업의 식별 근거, 탭·프레임 문맥 |
| 동작 | 실제 성공하는 입력·선택·조회·복귀 방법 |
| 준비·결과 조건 | 로딩 완료, 현재 검색 결과, 선택 완료, 저장 반영의 근거 |
| 업무 규칙 | 날짜·담당자·상태를 정하는 사용자 지시와 확인된 조건 |
| 저장·복구 | 변경 실행 지점, 저장 후 재조회 방법, 불확실한 결과의 중단 기준 |

확인하지 못한 값을 예제 문자열로 채워 실제 실행하지 마라. 기존 매크로가 있다면 그 구조에 맞춰 좁게 수정하라. 한 사이트의 특이 동작을 공통 실행기의 고정 동작으로 넣지 마라.

## 목록의 의미를 보존하라

- 시리얼·사번·주문번호 등 식별자는 원본 문자열을 유지하라. `2.51E+17`이나 앞자리 0을 임의의 정수로 복원하지 마라. 원본 손상이 의심되면 확인 가능한 원본과 구분하여 보고하라.
- 중복 조회 최적화와 중복 업무 제거는 다르다. 같은 번호여도 날짜·작업 지시·대상 레코드가 다르면 별개 업무일 수 있다. 조회를 공유해도 모든 원본 행에 결과가 연결되게 하라.
- 표시 날짜만 보고 완료로 판단하지 말고 실제 업무 상태 필드를 사용하라. 검색 결과가 여럿이면 사용자가 의도한 레코드 키를 먼저 확정하라.
- 결과 없음, 이미 완료, 처리 완료, 실패, 저장 결과 불명확을 구분하라. 오류를 결과 없음으로 바꿔 다음 건으로 넘어가지 마라.

## 상태를 기준으로 다음 단계로 이동하라

상태 예시를 업무에 맞게 줄이거나 바꾸라.

`조회 준비 → 결과 식별 → 상세 준비 → 값 입력·검증 → 저장 요청 → 저장 결과 확인 → 목록 복귀`

고정 시간 대기만으로 단계를 연결하지 마라. 로딩 지연에는 조건과 제한 시간을 두고, 단계 시작 전에 중단 요청을 확인하라. 정지 시 이미 전송된 변경은 취소되었다고 주장하지 말고 결과 확인이 필요한지 표시하라.

화면 전환 뒤 현재 문맥과 실행 코드의 연결 상태를 다시 확인하라. 재연결과 업무 동작 재실행을 분리하여 연결 복구가 저장 재클릭으로 이어지지 않게 하라.

스크롤이 바뀔 수 있으면 다음 버튼을 찾을 때 올바른 컨테이너에서 다시 표시되게 하라. 항상 맨 아래로 이동하거나 확인창을 두 번 누르는 순서를 모든 사이트에 고정하지 마라.

페이지 전환 중에도 조작 UI를 유지해야 한다면 해당 환경이 지원하는 사이드 패널 또는 별도 제어창을 선택하라. 진행 상태는 페이지 DOM 밖에서 보존하고 목록·업무 설정의 버전과 연결하라. 브라우저 전체에서 항상 패널이 보인다고 약속하지 마라.

## 불확실한 저장을 중복 실행하지 마라

저장 요청을 보내기 직전에 작업 키와 의도한 값을 기록하고, 결과 확인 전까지 `저장 결과 확인 중`으로 유지하라. 성공 알림만으로 충분한지 업무에 맞게 판단하고, 중요 변경은 목록 또는 상세 재조회에서 키와 변경 값이 반영됐는지 확인하라.

응답 유실, 화면 전환, 연결 오류가 저장 전인지 후인지 불명확하면 다음 순서를 따르라.

1. 같은 업무 키를 읽기 전용으로 재조회하라.
2. 요청한 상태가 반영됐다면 결과를 기록하고 이어가라.
3. 미반영이 확실하고 기존 요청이 아직 처리 중이지 않다는 근거가 있을 때만 기존 승인 범위에서 재시도하라.
4. 판별할 수 없으면 해당 건을 보류하고 상태·확인 필요 사항을 알려라. 위험에 따라 해당 건 또는 전체 실행을 멈추라.

지원 API에 멱등성 키가 있으면 그 공식 의미에 따라 사용하라. 임의 필드를 추가하거나 로컬 진행 기록만으로 서버 중복 방지가 보장된다고 판단하지 마라.

## 재개와 검증을 업무에 맞추라

재개 정보에 원본 목록 식별, 설정, 현재 업무 키, 마지막 확인된 단계, 저장 확인 상태를 포함하라. 마지막 클릭이 아니라 마지막으로 검증한 결과에서 복구하라. 목록·날짜 규칙이 바뀌었다면 이전 커서를 그대로 적용하지 마라.

변경 없는 점검과 실제 저장 실행을 구분하고, ‘1건 실행’이 저장까지 포함하면 버튼이나 안내에 표시하라. 이미 현재 요청에서 승인된 작업을 반복 확인받을 필요는 없지만, 다른 업무의 승인을 가져오지는 마라.

검증은 고친 위험에 집중하라. 예를 들어 검색 준비 지연, 중복 라벨, 다른 달력 시작 연도, 지연된 이전 응답, 저장 응답 유실 중 실제 관련된 상황을 확인하라. 테스트 개수보다 어떤 동작과 실패 상황을 검증했는지 설명하라.
