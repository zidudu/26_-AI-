# GitHub Deep Search

GitHub를 중심으로 사용자의 작업에 도움이 되는 기존 구현과 오픈소스를 찾는다.

단순히 관련 저장소 목록을 나열하는 데서 끝내지 않고,
실제로 참고하거나 가져다 사용할 가치가 있는 코드와 구현을 찾아내는 것이 목적이다.

## 기본 원칙

사용자의 요청을 먼저 이해하고,
상황에 맞는 검색 전략과 탐색 깊이를 스스로 결정한다.

고정된 절차에 얽매이지 않는다.

필요에 따라 다음 자료를 자유롭게 활용한다.

- GitHub repositories
- GitHub code search
- README 및 프로젝트 문서
- 실제 소스 파일
- Issues
- Pull Requests
- Commits
- Releases
- Examples 및 Tests
- 공식 문서
- 웹 검색
- 개발자 커뮤니티

모든 작업에서 위 자료를 전부 조사할 필요는 없다.

간단한 요청은 빠르게 처리하고,
복잡하거나 실제 코드 재사용이 필요한 요청은 더 깊게 조사한다.

## 검색 전략

사용자가 입력한 문장을 그대로 한 번 검색하고 끝내지 않는다.

필요하면 검색어를 스스로 확장하거나 바꾼다.

예를 들어 다음 요소를 활용할 수 있다.

- 기술명
- 관련 기술 또는 대체 기술
- 라이브러리 이름
- 알고리즘 이름
- 구현 방식
- 함수 또는 클래스 이름
- 파일 이름
- 오류 메시지
- 로그 메시지
- API 이름
- 설정값
- 프레임워크
- 프로그래밍 언어

탐색 중 더 좋은 키워드나 프로젝트를 발견하면
처음 세운 방향보다 새롭게 발견한 단서를 우선할 수 있다.

## 저장소 탐색

유명하거나 Star가 많은 저장소라는 이유만으로 선택하지 않는다.

사용자의 현재 작업에 실제로 도움이 되는지를 중심으로 판단한다.

필요에 따라 다음을 살펴본다.

- 요청한 기능과의 적합성
- 코드 구조와 품질
- 이해하기 쉬운 정도
- 재사용하기 쉬운 정도
- 유지보수 상태
- 최근 업데이트
- 문서
- 예제
- 테스트
- 의존성
- 라이선스

작고 단순한 구현이 더 적합하다면
대형 프로젝트보다 우선할 수 있다.

좋은 후보가 하나 명확하다면 불필요하게 많은 저장소를 비교하지 않는다.

반대로 판단이 어렵다면 여러 후보를 비교한다.

## 코드 탐색

유용한 저장소를 발견했다면 필요에 따라 실제 소스까지 확인한다.

README 설명만 보고 구현을 추측하지 않는다.

다음과 같은 질문에 답할 수 있을 정도로 필요한 만큼 코드를 탐색한다.

- 실제 기능은 어느 파일에서 구현되는가?
- 핵심 함수나 클래스는 무엇인가?
- 어디에서 호출되는가?
- 어떤 코드에 의존하는가?
- 현재 프로젝트에서 독립적으로 사용할 수 있는가?
- 특정 프레임워크나 구조에 강하게 묶여 있는가?

필요하면 관련 파일과 호출 관계를 따라가며 확인한다.

단, 작은 요청에 과도한 분석을 하지 않는다.

## Issues / Pull Requests / Commits

코드만 보고 판단하기 어렵거나
버그, 호환성, 변경 이유, 최신 상태가 중요한 경우 활용한다.

예를 들어 다음과 같은 경우 탐색할 수 있다.

- 코드와 문서의 내용이 다를 때
- 오래된 구현인지 확인해야 할 때
- 특정 오류가 이미 보고되었는지 확인할 때
- 최근 API 변경이 있었을 때
- 특정 구현이 왜 변경되었는지 알아야 할 때
- 유지보수 중인 대체 구현이나 fork를 찾을 때

항상 확인해야 하는 필수 단계는 아니다.

## 오픈소스 재사용

사용자가 기존 구현을 현재 작업에 활용하려 한다면
단순한 링크 제공보다 실제 활용 가능성을 판단한다.

상황에 따라 다음 중 적절한 방법을 선택한다.

- 원본 프로젝트를 그대로 사용
- 패키지나 라이브러리로 설치
- 특정 파일을 활용
- 특정 함수나 클래스만 참고
- 핵심 알고리즘만 가져와 다시 구현
- 현재 프로젝트 구조에 맞게 수정
- 더 적합한 다른 구현을 다시 검색

"오픈소스를 찾았다"는 사실보다
"현재 작업에 실제로 어떻게 사용할 수 있는가"가 더 중요하다.

## 라이선스

실제 코드나 자산을 재사용하려는 경우 라이선스를 확인한다.

라이선스가 없거나 조건이 불분명하면
자유롭게 복사할 수 있다고 가정하지 않는다.

사용자에게 필요한 수준에서 다음과 같은 주의점을 알려준다.

- 출처 표시 필요 여부
- LICENSE 또는 NOTICE 유지 여부
- 수정 및 배포 조건
- 소스 공개 조건 가능성
- 상업적 사용 관련 조건
- 라이선스가 없는 경우의 위험

법률 자문처럼 단정하지 않는다.

## 최신성 및 호환성

변화가 빠른 기술에서는 오래된 예제를 그대로 사용하지 않는다.

필요하면 다음을 확인한다.

- 최근 commit
- 최근 release
- 현재 문서
- dependency version
- deprecated API
- 현재 플랫폼 또는 언어 버전과의 호환성

오래된 구현이라도 구조나 알고리즘이 유용하면 참고할 수 있다.

이 경우 현재 환경에서 변경해야 할 부분을 구분해 설명한다.

## 공식 자료와 웹 검색

GitHub만으로 충분하지 않다면 외부 검색을 사용한다.

가능하면 다음과 같은 자료를 우선한다.

- 프로젝트 공식 문서
- 공식 홈페이지
- 공식 패키지 문서
- 기술 문서
- 개발자 커뮤니티
- 신뢰할 수 있는 기술 자료

외부 자료는 GitHub에서 찾은 구현을 이해하거나 검증하기 위한 보조 수단으로 활용한다.

GitHub 자료와 공식 문서가 충돌하면
가능한 한 최신 공식 정보를 기준으로 판단한다.

## 실제 프로젝트와 연결

사용자가 자신의 코드나 프로젝트를 함께 제공했다면
검색 결과를 별개의 자료로 끝내지 않는다.

필요한 경우 다음까지 이어서 수행한다.

- 기존 프로젝트 구조 이해
- 찾은 오픈소스와 구조 비교
- 사용할 수 있는 부분 식별
- 충돌하는 dependency 또는 API 확인
- 필요한 코드 수정
- 현재 프로젝트에 맞게 통합
- 가능한 범위에서 동작 검증

검색은 구현을 돕기 위한 수단이다.

## 결과 전달

검색 과정을 장황하게 나열하지 않는다.

사용자가 판단하거나 바로 활용할 수 있는 내용 중심으로 설명한다.

상황에 따라 다음 정보를 포함할 수 있다.

- 가장 유용한 프로젝트 또는 구현
- 왜 적합한지
- 관련 저장소
- 핵심 파일
- 핵심 함수 또는 클래스
- 적용 방법
- 필요한 의존성
- 호환성 문제
- 라이선스
- 다른 대안

사용자가 자세한 조사 과정을 원하면 그때 더 깊게 설명한다.

## 판단의 유연성

이 스킬의 규칙보다 사용자의 실제 목적을 우선한다.

검색 횟수,
후보 개수,
조사할 파일,
분석 깊이,
사용할 도구를 미리 고정하지 않는다.

좋은 단서를 발견하면 그 방향으로 깊게 들어가고,
가치가 낮은 탐색은 빠르게 중단한다.

필요하다면 GitHub 밖으로 검색 범위를 넓히거나
다른 구현 방식을 제안할 수 있다.

## 핵심 목표

이 스킬의 목적은
"관련 GitHub 저장소를 많이 찾는 것"이 아니다.

사용자의 작업을 더 빠르고 안정적으로 해결할 수 있도록
기존 오픈소스와 실제 구현 사례를 탐색하고,
그중 가치 있는 내용을 찾아 현재 작업에 연결하는 것이다.
